# 《闪切协议》工程规范

> 适用于 6 人 9 天实训（Unity 6000.3.7f1 / Built-In 2D / Mono 构建）。
> 这份文件的目的只有一个：**让六个人写出来的东西长得一样，D5 合并时不打架。**
> 落地方式：把本文放到仓库 `docs/工程规范.md`，10/31 全员过一遍，之后谁新建文件就照这个来。

---

## 0. 为什么必须先定规范

不夸张地说，**六个新生项目死得最快的方式不是写不出功能，是文件找不到、名字对不上、合并冲突**。

三个真实会发生的场景：

- 美术给了你 `玩家.png`、`玩家2.png`、`玩家最终版.png`，你不知道该用哪个，全塞进项目，最后上线的那个是错的
- 两个程序都写了 `ObjectPool.cs`，Unity 报 `duplicate class`，谁也看不懂是哪来的
- 有人 `git add .` 把 `Library/`（三个 G）提交了，之后所有人 clone 都卡住

**这三件事都不需要"技术能力"来解决，只需要一份规则。** 所以规范不是形式主义，是省时间的。

---

## 1. 四条铁律（其余都可以商量，这四条不行）

| # | 规则 | 为什么不可商量 |
|---|---|---|
| 1 | **文件名一律用英文，不用中文、不用空格** | Unity 对中文路径有各种诡异问题；打包时某些工具会挂；Git 在 Windows 上对中文文件名处理不一致 |
| 2 | **文件名不允许出现版本词**：`new` `final` `old` `2` `(1)` `改` | 出现"最终版"的那一刻，就说明没有版本控制了——而你们有 Git |
| 3 | **文件名 = 类名（脚本）** | Unity 里 MonoBehaviour 挂载要求类名与文件名一致，不一致的脚本挂不上 |
| 4 | **一旦定名，不再改** | 改文件名会让 Unity 生成新的 `.meta`，引用全部断裂（预制体上的脚本会变成 `Missing`）。改名成本远高于当初想清楚 |

> 第 4 条尤其重要。**宁可名字起得笨一点，也不要第二天觉得"不太对"就重命名。** 真要改，必须走"改名 + 提交 + 全员 pull"的流程，而且没人有本地未提交改动时才能做。

## 2. 命名规范（按类型分）

### 2.1 代码

| 对象 | 规则 | 例 |
|---|---|---|
| 脚本文件 | `PascalCase`，与类名完全一致 | `PlayerController.cs`、`SlashSystem.cs` |
| 类 / 结构体 / 枚举 | `PascalCase` | `class EnemyManager` |
| 公开方法 / 属性 | `PascalCase` | `TakeDamage()`、`IsCharging` |
| 私有字段 | `camelCase` | `chargeSpeed`、`lastSlashAt` |
| 局部变量 / 参数 | `camelCase` | `worldDt`、`targetEnemy` |
| 常量 | `PascalCase` | `MaxEnemyCount`、`ChargeTier2Threshold` |
| 接口 | `I` + `PascalCase` | `IDamageable` |
| 事件 | `On` + 动词过去式 / 名词 | `OnEnemyDied`、`OnLevelUp` |

**硬要求两条：**

- **不要写 `public` 字段。** 用 `[SerializeField] private float chargeSpeed;`。public 字段会污染 Inspector，而且谁都能改，出了问题查不到。
- **类名必须带模块语义。** 写 `EnemyChaser`，不要写 `Chaser`；写 `UIScoreBar`，不要写 `Bar`。三个程序各写各的，短名字一定会撞。

**关于命名空间**：统一使用 `namespace FlickCut`，所有脚本都加，包括空文件。

> 与仓库名对齐：仓库是 `FLICKCUT-PROTOCOL`，所以代码里一律 `FlickCut`（一个单词、驼峰），**不要写 `FlashCut`、`FlickCut.Protocol`、`FLICKCUT`**。
> 顺手加一条硬的：**Unity 里 `Product Name` 填 `FLICKCUT PROTOCOL`，`Company Name` 填 `FlickCut`**，六个人建项目时都要一致——不一致会导致 `PlayerPrefs` 路径不同，D6 之后存档/设置会莫名消失。

```csharp
namespace FlickCut
{
    public class PlayerController : MonoBehaviour
    {
        // ...
    }
}
```

**要么全都加、要么全都不加，10/31 定死后不许变。** 一半加一半不加，引用会到处报"找不到类型"，而且报错信息看不出原因。

### 2.2 场景 / 预制体 / 数据资产

| 对象 | 规则 | 例 |
|---|---|---|
| 场景 | `PascalCase` | `Boot.unity`、`Arena.unity`、`Dev_A.unity` |
| 预制体 | `PascalCase`，多词用 `_` 分隔模块与具体 | `Player.prefab`、`Enemy_Chaser.prefab`、`VFX_Slash.prefab` |
| ScriptableObject 资产 | `snake_case`，带类型前缀 | `upgrade_widen.asset`、`config_base.asset` |
| 材质 | `mat_` + `snake_case` | `mat_enemy_cyan.mat` |
| 动画剪辑 | `anim_` + `snake_case` | `anim_player_idle.anim` |

**`Dev_*` 场景的规则**：每人一个（`Dev_A` / `Dev_B` / `Dev_C`），自己随便玩，**可以提交，但不能出现在最终构建里**。

### 2.3 美术资源（两个人以上协作时最容易乱）

统一用 **`前缀_小写下划线`**。前缀决定它是哪类东西：

| 前缀 | 用途 | 例 |
|---|---|---|
| `spr_` | Sprite 单图（角色、敌人、场景件） | `spr_player_base.png`、`spr_enemy_chaser.png` |
| `ui_` | UI 元素（面板、按钮、卡面、HUD） | `ui_card_bg.png`、`ui_hp_bar_fill.png` |
| `vfx_` | 特效贴图 | `vfx_slash_glow.png` |
| `tex_` | 平铺底图 / 网格 | `tex_arena_grid.png` |

**同一角色的多帧/多变体，用后缀区分，不要用数字堆：**

```
spr_player_base.png
spr_player_charge.png      ← 蓄力状态的形态
spr_enemy_chaser_base.png
spr_enemy_chaser_hurt.png
```

**不许出现的中文名**（真实会发生的）：

```
❌ 玩家.png        ✅ spr_player_base.png
❌ 三角形敌人.png   ✅ spr_enemy_chaser.png
❌ 刀光-宽.png      ✅ vfx_slash_wide.png
❌ 新文件夹 (2)      ✅ （不要建这个文件夹）
```

### 2.4 音频

| 前缀 | 用途 | 例 |
|---|---|---|
| `sfx_` | 短音效（≤ 3 秒） | `sfx_slash_tier1.wav`、`sfx_hit_soft.wav` |
| `bgm_` | 背景音乐（循环） | `bgm_arena_loop.ogg` |

**三段蓄力的音效要能对上**：`sfx_charge_tier1` / `tier2` / `tier3`。这样程序接入时不用问美术"哪个是第一段"。

## 3. 存放规范

### 3.1 判定一个文件该放哪（照着走，不要自己建目录）

```
这个文件是……
├─ C# 脚本        → Assets/_Project/Scripts/<模块>/
├─ 图片            → Assets/_Project/Art/<分类>/
├─ 音频            → Assets/_Project/Audio/SFX/ 或 Music/
├─ 预制体          → Assets/_Project/Prefabs/
├─ 材质 / 动画      → Assets/_Project/Art/ 对应子目录
├─ 数值配置        → Assets/_Project/Data/
├─ 文档            → docs/
├─ 只是自己试验的    → Assets/_Scratch/<你的名字>/
└─ 不确定           → 问技术负责人，不要自己建目录
```

**最后一条是纪律，不是客气。** 六个人各建一个"我觉得这样更合理"的目录，D4 就没人找得到东西了。

### 3.2 模块目录只有六个，不许新增

`Scripts/` 下只允许这六个：

```
Scripts/
├─ Core/      GameFlow.cs  ObjectPool.cs  GameConfig.cs
├─ Player/    PlayerController.cs  ChargeController.cs
├─ Combat/    SlashSystem.cs  IDamageable.cs  HitFeedback.cs
├─ Enemy/     EnemyBase.cs  EnemyChaser.cs  EnemyTank.cs  EnemyManager.cs
├─ Build/     UpgradeDef.cs  UpgradeManager.cs
└─ UI/        HUD.cs  LevelUpPanel.cs  ResultPanel.cs
```

一个脚本放哪个模块，看**它属于谁的生命周期**，不是看谁写的：

- 敌人身上的逻辑 → `Enemy/`（哪怕是我写的）
- 屏幕上显示的 → `UI/`
- 两个模块都要用的工具 → `Core/`

### 3.3 临时区 `_Scratch`（必须有，而且要进 .gitignore）

新生一定会写测试脚本、放临时贴图。**不给地方，他们就会丢进正式目录。**

```
Assets/_Scratch/<你的名字>/      ← 例如 Assets/_Scratch/mqz/
```

`.gitignore` 加一行：

```
Assets/_Scratch/
```

好处有两个：谁都敢在里面乱试；而且**不会有人把测试脚本提交上去，让技术负责人猜"这个 TestSlash2.cs 要不要删"**。

### 3.4 仓库里不该有的东西（`git add .` 前必看）

| 不该有 | 后果 |
|---|---|
| `Library/` `Temp/` `Obj/` `Logs/` `UserSettings/` | 几百 MB 到几个 G，每人不同，提交必冲突 |
| `*.csproj` `*.sln` `*.user` `.vs/` | Unity 自动生成，提交必冲突 |
| `Build/` 里的 exe | 走 Release 附件 |
| 大于 50MB 的 PSD / AI 源文件 | 走网盘，仓库只放导出后的 png |
| `Assets/_Scratch/` | 临时区不进仓库 |
| 授权不明的字体、音乐 | 答辩会被问来源 |

> **`.gitignore` 里的目录规则必须带前导 `/`，锚定到仓库根。**
> 已踩过一次：原规则裸写 `Build/`，把 `Assets/_Project/Scripts/Build/`（卡池模块）一起忽略了，该目录从头到尾没进过版本库。**症状是"文件我明明建了，`git status` 里看不到"**，新手会以为编辑器没保存，能查半天。
> 正确写法：`/Build/`、`/Library/`、`/Temp/`、`/[Bb]uilds/`。**新增忽略规则时，先跑 `git check-ignore -v <你的文件>` 确认它有没有被误伤**。

### 3.5 功能分级与代码归属（P0 / P1 / P2 ↔ 文件）

**排期按 P 编号走（见启动方案 §1.5）。这一节解决"某个 P 编号该改哪个文件"，避免两个人改同一个文件。**

| 编号 | 功能 | 主要落在哪个文件 | 谁维护 |
|---|---|---|---|
| **P0-1** | 移动 + 瞄准 | `Player/PlayerController.cs` | 程序 1 |

| **P0-3** | 切割命中 | `Combat/SlashSystem.cs`、`Combat/IDamageable.cs` | 程序 1 |
| **P0-4** | 死亡 → 经验 | `Enemy/EnemyBase.cs`、`Enemy/EnemyManager.cs`、`Build/UpgradeManager.cs`（经验条） | 程序 2 |
| **P0-5** | 升级三选一 | `Build/UpgradeDef.cs`、`Build/UpgradeManager.cs`、`UI/LevelUpPanel.cs` | 程序 2 |
| **P0-6** | 一局闭环 | `Core/GameFlow.cs`、`UI/ResultPanel.cs` | 程序 2（`GameFlow` 改动须程序 1 过目） |
| **P0-7** | 三色可分辨 | `Art/` 与 `Data/GameConfig.asset` 里的颜色 | 美术 A |
| **P0-8** | 能出包 | Build Profiles、`README.md` 的"怎么跑" | 程序 3 |
| **P0-9** | 能重开 | `Core/GameFlow.cs` 的 `ResetRun()`、`Core/ObjectPool.cs` | 程序 3 测 / 程序 1 修 |
| **P1-1** | 三段蓄力 | `Player/ChargeController.cs` | 程序 1 |
| **P1-2** | 4 张卡 | `Build/UpgradeDef.cs` + `Data/Upgrades/*.asset` | 程序 2 |
| **P1-3** | 两类敌人 | `Enemy/EnemyTank.cs`、`Enemy/EnemyManager.cs` | 程序 2 |

**三条由此推出的规矩：**

1. **同一时刻，一个文件只有一个主人。** 想改别人的文件，先在群里说，对方当天不做那块。
2. **`GameFlow.cs` 是全场唯一的多入口文件**，所有改动都要程序 1 过目——因为时间缩放、暂停、结算、重开全挤在这一个文件里，冲突也全在这里。

## 4. C# 代码规范（精简到能记住的程度）

不强求风格统一到"每行几个空格"，只要求下面这几条，因为它们直接影响**能不能改得动**。

### 4.1 文件结构

```csharp
using UnityEngine;

namespace FlickCut
{
    /// <summary>玩家移动、瞄准与蓄力输入的入口。</summary>
    public class PlayerController : MonoBehaviour
    {
        [SerializeField] private float moveSpeed = 220f;
        [SerializeField] private float chargeSlowFactor = 0.65f;

        private bool isCharging;
        private float chargeProgress;

        public bool IsCharging => isCharging;
        public float ChargeProgress => chargeProgress;

        private void Update()
        {
            // ...
        }

        public void BeginCharge() { /* ... */ }
    }
}
```

### 4.2 五条硬要求

1. **一个文件一个 `public` 类**，文件名与类名相同。
2. **不写 `public` 字段**，用 `[SerializeField] private` 暴露给 Inspector。
3. **不用 `Region`**。需要分区的类，说明它该拆了。
4. **每个 `public` 方法上方写一行中文 `/// <summary>`**。不是为了好看——**是为了 D8 出 bug 时，别人（或明天的你）能看懂这是在干什么**。
5. **魔法数字要么进 `GameConfig`，要么写成常量**。`if (progress >= 0.65f)` 里的 `0.65` 必须能查到出处（数值表里有）。

> 第 5 条是这次特别要盯的。手感参数会反复调，散落在十个文件里的 `0.65` 根本改不动。

### 4.3 明确不做的事

- 不写单例管理器（除了 `GameFlow` 一个，且由技术负责人维护）
- 不写通用框架、事件总线、数据驱动卡池（**4 张卡写死就行**）
- 不用 `FindObjectOfType` 到处找对象（Unity 6 里这个方法已废弃，改用引用或事件）

## 5. Git 规范

> **新人先看 §5.9「一个功能的完整流程」——八步走完一次，再回来看下面的细则。**

### 5.0 开工前的 Git 配置与 SSH 连接（每人做一次，不可省略）

> **硬性要求：六个人全部用 SSH 连接 GitHub，不使用 HTTPS。**
> 本章按顺序做完 4 步，做完在群里报一句"`ssh -T` 显示我的用户名了"。

#### 5.0.1 Git 身份与行为配置（4 行）

装完 Git for Windows 后，打开 Git Bash 执行（把名字和邮箱换成自己的）：

```bash
git config --global user.name  "马权"
git config --global user.email "你的GitHub邮箱"
git config --global core.autocrlf false
git config --global core.longpaths true
```

| 这行为什么必须有 |
|---|
| **`user.name` / `user.email`** 不配的话，六个人的提交全显示成别人的名字，`git log` 查不到责任人。**邮箱用注册 GitHub 的那个**，否则 GitHub 不认这个提交是你的 |
| **`core.autocrlf false`** 仓库里 `.gitattributes` 已统一 `eol=lf`，客户端再自动转换会与它冲突，表现是"我没改的文件显示全变了" |
| **`core.longpaths true`** Unity 的 `Library/` 和素材路径很深，路径超过 260 字符时 Git 会直接失败 |

**Git 版本要求（和 Unity 不同，不需要六人一致）**

| 项 | 要求 |
|---|---|
| 最低版本 | **2.40 以上**（2023 年发布） |
| 六人是否需要"一字不差" | **不需要。** Git 的仓库格式与传输协议向后兼容，`clone` / `push` 不受版本差异影响，本项目也没有使用任何新格式特性。**这一点和 Unity 正好相反——Unity 必须六人完全一致，Git 不必** |
| `2.55.0.windows.3` 与 `2.55.0.windows.5` 有区别吗 | **没有功能区别。** `.windows.N` 是同一版本号下的不同构建批次（补丁级重编译），二者可互操作 |
| 怎么查 | `git --version`（同时确认 `ssh -V` 有输出，SSH 客户端随 Git 附带） |
| 低于 2.40 怎么办 | 直接装最新版覆盖安装即可，不需要先卸载，用户级配置（`~/.gitconfig`）会保留 |

#### 5.0.2 为什么是 SSH 而不是 HTTPS

三条理由，都是这 9 天里会实际发生的：

| 理由 | HTTPS 的问题 | SSH 的表现 |
|---|---|---|
| 凭据会失效 | 靠 Credential Manager 存个人访问令牌，令牌有有效期、会被撤销。失效后报 `Authentication failed`，**看不出是过期还是没权限** | 密钥不失效，除非在 GitHub 上手动删除 |
| 身份不可自证 | 凭据是 Git 代填的，出问题时分不清用的是谁的、推到哪个账号 | `ssh -T git@github.com` 一条命令直接回答"我是谁" |
| 每天要推一次 | 本项目每晚 23:00 必须 push，认证链路必须可自检 | 同上，失败时能定位到具体环节（端口 / 密钥 / 权限） |

#### 5.0.3 第 1 步：生成密钥

```bash
ssh-keygen -t ed25519 -C "你的名字@flickcut"
```

- **保存位置**：直接回车，用默认的 `~/.ssh/id_ed25519`
- **密码短语（passphrase）**：**直接回车，不设**。这是只用于本仓库读写的项目密钥，六个人各自私人电脑、周期 9 天；设了就必须配 `ssh-agent`，新生配不好会变成每次 push 都要输密码甚至失败。**只有电脑与他人共用时（宿舍公用机、家里共用），才设密码短语**
- 如果提示 `~/.ssh/id_ed25519 already exists`：**说明已有密钥，不要覆盖**，直接跳到第 2 步用现有那把

#### 5.0.4 第 2 步：把公钥贴到 GitHub

```bash
clip < ~/.ssh/id_ed25519.pub
```

GitHub 网页 → 右上头像 → **Settings** → **SSH and GPG keys** → **New SSH key** → Title 填自己名字 → Key 粘贴 → **Add SSH key**

**只贴 `.pub` 结尾的那一个文件。** 贴成不带 `.pub` 的私钥会报 `Key is invalid`；私钥本身绝不能发给任何人、也不能进仓库。

#### 5.0.5 第 3 步：验证（必须看到自己的账号名）

```bash
ssh -T git@github.com
```

第一次会问 `Are you sure you want to continue connecting?`，输 `yes` 回车。成功的样子：

```
Hi jmx2033! You've successfully authenticated, but GitHub does not provide shell access.
```

**`Hi` 后面必须是自己的 GitHub 账号名。** 如果显示的是别人的名字，说明贴的是别人的密钥，或这台机器上有别的密钥被优先选中——停下来找策划，不要继续 commit。

#### 5.0.6 第 4 步：22 端口不通时改走 443（校园网常见，与密钥无关）

现象：`ssh -T` 卡十几秒后报 `Connection timed out` 或 `Connection refused`。原因是校园网或部分运营商封了 22 端口，**不是密钥问题**。

解决：让 GitHub 的 SSH 走 443 端口。在 Git Bash 里一条命令写完：

```bash
printf 'Host github.com\n  Hostname ssh.github.com\n  Port 443\n  User git\n' > ~/.ssh/config
```

再执行一次 `ssh -T git@github.com`。

> 加了这段配置后，`ssh -T git@github.com` 实际连接的是 `ssh.github.com:443`，但返回的仍是 GitHub 的认证结果，属正常。**本机已用此配置实测通过。**
> 没有这个文件时手动新建：路径 `C:\Users\<用户名>\.ssh\config`，无扩展名。

#### 5.0.7 第 5 步：用 SSH 地址克隆（不是 https）

```bash
git clone git@github.com:jmx2033/FLICKCUT-PROTOCOL.git
```

**判断标准：地址以 `git@github.com:` 开头。带 `https://` 的一律不合规。**

已经用 HTTPS 克隆过的，改一行即可，不用重新克隆：

```bash
git remote set-url origin git@github.com:jmx2033/FLICKCUT-PROTOCOL.git
git remote -v      # 两行都必须以 git@github.com: 开头
```

#### 5.0.8 SSH 报错对照表（照表处理，不要凭感觉重装）

| 报错 | 原因 | 处理 |
|---|---|---|
| `Permission denied (publickey)` | GitHub 上没有这把公钥，或贴错了文件 | 重做 5.0.4 |
| `Connection timed out` / `Connection refused` | 网络封了 22 端口 | 做 5.0.6 改走 443 |
| `Key is invalid` | 贴成了私钥，或复制不完整 | 重新 `clip < ~/.ssh/id_ed25519.pub` |
| `Hi 别人的名字` | 这台机器选中了别人的密钥 | 检查 `~/.ssh` 与 `~/.ssh/config`，找策划核对 |
| `Host key verification failed` | `known_hosts` 里有该主机的旧记录 | `ssh-keygen -R github.com` 后重试 |
| `Repository not found` | 不是 collaborator，或地址拼错 | 确认邀请邮件已点，地址一字不差 |

> **HTTPS 只在 SSH 在本机确实无法连通、且已找策划登记的情况下作为临时兜底**，用完当晚会前要改回 SSH。理由见 5.0.2。

### 5.1 分支

| 类型 | 格式 | 例 | 谁用 |
|---|---|---|---|
| 功能 | `feat/<模块>-<简述>` | `feat/slash-tiers` | 程序 |
| 修复 | `fix/<简述>` | `fix/exp-orb-pool` | 程序 |
| 美术 | `art/<内容>` | `art/player-sprite` | 美术 |
| 文档 | `docs/<内容>` | `docs/scope-list` | 策划 |

**三条纪律：**

- **每人同时只允许 1 个活跃分支**，合并完再开下一个
- **分支存活不超过 2 天**，超过就说明拆分有问题
- **分支只从最新的 `main` 开**，不从别人的分支开

### 5.2 提交信息（本地钩子 + CI 双层强制）

格式固定：

```
<type>(<scope>): <一句话说清改了什么> [P编号]
```

| 字段 | 可选值 / 要求 |
|---|---|
| `type` | `feat` 新功能 / `fix` 修 bug / `art` 美术资源 / `docs` 文档 / `chore` 杂务 / `refactor` 重写不改行为 |
| `scope` | **只有这 7 个**：`charge` `slash` `enemy` `ui` `build` `repo` `levelup`。**仓库、流程、CI、文档类改动一律用 `repo`**，不要新造 `git` `scope` `player` 之类的词 |
| 描述 | 中文，说清改了哪个功能、改成什么样。**不少于 4 字，末尾不加句号**，标题总长建议 ≤ 72 字符 |
| `[P编号]` | **`feat` / `fix` / `art` 必须带**（`[P0-3]` `[P1-4]`）。**`scope=repo` 不要求**——它是仓库与工程维护，不属于 P0/P1/P2 功能分级 |

**美术提交的 `scope` 按"这张图用在哪"填**：卡面/HUD 用 `ui`，敌人造型用 `enemy`，刀光用 `slash`，蓄力表现用 `charge`。

**双层校验（10/31 起生效）：**

| 层 | 什么时候拦 | 要不要装东西 |
|---|---|---|
| 本地 `commit-msg` 钩子 | `git commit` 当场拦截，不用等 CI | clone 后执行一次 `bash Tools/ci/install-hooks.sh`（只用 Git Bash 自带的命令，**不需要装 Python**） |
| CI | PR 上逐条检查本次 PR 引入的提交 | 已在 `.github/workflows/ci.yml`，无需安装 |

**不要用 `git commit --no-verify` 绕过钩子。** 绕过只是把报错推迟到 PR 上，全队多看一轮。觉得规则不合理，找策划改规则，不要绕。

**正例（都能通过钩子与 CI）：**

```
feat(slash): 三段刃形按蓄力进度切换 [P1-1]
fix(enemy): 敌人死亡后经验球未回收 [P0-4]
art(ui): 卡面描边加粗到 2px [P1-5]
docs(repo): 补做/不做清单
chore(repo): 忽略 Library 与 _Scratch
```

**反例：**

```
❌ update
❌ 改了一下
❌ 最终版
❌ feat(slash): 三段刃形按蓄力进度切换      ← feat 缺 P 编号
❌ feat(player): 玩家移动 [P0-1]            ← scope 只有 7 个，没有 player
❌ art(player): 玩家基础造型 64px [P1-5]    ← scope 同上
❌ fix(enemy): 修好了。 [P0-4]              ← 末尾不加句号，且"修好了"没说清修了什么
```

判断标准很简单：**三天后你自己能不能看懂这条提交在干什么。**

另外两条不写进格式、但照样要遵守：

- **一次提交只做一件事。** 不要把"改蓄力手感"和"换卡面"塞进同一条提交，出问题时没法单独回退
- **提交前必须本地能编译、能 Play**（见 §5.3）。CI 不跑 Unity，编译错误只有你自己能提前发现

### 5.3 提交前必做（`git add` 之前）

```bash
git status          # 先看一遍，确认没有 Library、没有 exe、没有 .csproj
git add <具体文件>   # 尽量不用 git add .
git commit -m "feat(slash): 三段刃形按蓄力进度切换 [P1-1]"   # 钩子会当场校验格式
```

**关于 `git add .`**：不是禁用，但**每次用它之前必须先 `git status` 看一眼**。六个人里一定有人会在某天用它把 `Library/` 提交上去，那天所有人的 clone 都会变慢十倍。

### 5.4 PR（Pull Request）

- 标题同提交规范，**末尾标 P 编号**：`feat(slash): 三段刃形按蓄力进度切换 [P1-1]`
- 描述三行：
  ```
  改了什么：蓄力进度映射到三段刃形
  怎么验证：Arena 场景按住左键，看刀的长宽变化
  截图/录屏：有视觉变化时必传
  ```
- **至少 1 人 review 后才能合并**（三个程序互审，美术/文档可由策划审）
- **24 小时内必须有人看**。超时没人看的 PR，说明分工出了问题
- **一个 PR 只做一件事**，超过 400 行就拆

### 5.5 六条禁止（写进 PR 模板底部）

```
[ ] 没有提交 Library/ Temp/ Obj/ *.csproj *.sln
[ ] 没有提交 Assets/_Scratch/
[ ] 没有修改 Arena.unity（除非我是技术负责人）
[ ] 没有 force push
[ ] 没有残留冲突标记 <<<<<<< 或 >>>>>>>
[ ] 本地能跑起来（拉最新 main 后编译通过）
```

### 5.6 每天的时间节奏

| 时间 | 做什么 |
|---|---|
| 早上开工 | `git pull` → 打开项目确认能跑 → 有错先修，不要开始写新东西 |
| 写的过程中 | 每完成一个小功能就 commit + push（**不攒到晚上**） |

**"攒到晚上一次推"是新手最常见的坏习惯。** 攒了一天的改动，冲突时几乎无法解决；每两小时推一次，冲突只有几行。

### 5.7 场景文件与预制体的特殊规则

`.unity` 和 `.prefab` 是**二进制式文本，无法有效合并**。所以：

| 文件 | 谁可以改 |
|---|---|
| `Arena.unity` | **只有技术负责人** |
| `Dev_A/B/C.unity` | 各自的主人 |
| `Player.prefab` | 技术负责人 |
| `Enemy_*.prefab` | 系统程序 |
| UI 预制体 | 工具/测试程序 + 美术B |
| 别人的预制体 | **改之前先在群里说一声** |

> 这条不遵守的后果很具体：两个人同时改 `Arena.unity`，合并时 Git 会说 `Cannot merge binary files`，最后只能丢掉一个人的全部改动。

### 5.8 美术提交的特殊提示

美术同学最容易踩的两件事：

1. **提交前先改名成规范格式**，不要提交 `新建图层1.png` 再让程序改
2. **每完成一张就提交一次**，不要攒十张一起提交。**你的电脑是这些图的唯一副本**，坏了就没了

### 5.9 一个功能的完整流程（八步，照这个顺序走）

> 这一节是 §5.1–§5.8 的串联。**新人第一天就把这八步走一遍**（哪怕只改 README 里一行），比读八节规则有用。
> 当前状态：八步全部生效。第 5 步 CI 只做静态检查，不跑 Unity，细则见 §5.10。

| 步 | 做什么 | 命令 / 操作 | 做完的判据 |
|---|---|---|---|
| 1 | 更新 `main`，切新分支 | `git switch main`<br>`git pull`<br>`git switch -c feat/slash-tiers` | `git branch` 显示当前在 `feat/...`，前缀符合 §5.1 |
| 2 | 写代码 | 只改自己负责的文件（归属见 §3.5）；**不动别人的 `.unity` / `.prefab`**（§5.7） | 编辑器能编译、能 Play |
| 3 | 提交**并推送** | `git status`<br>`git add <具体文件>`<br>`git commit -m "feat(slash): 三段刃形按蓄力进度切换 [P1-1]"`<br>`git push -u origin feat/slash-tiers` | 网页上能看到这个分支和它的提交 |
| 4 | 开 PR | 网页 → **Pull requests → New pull request**，base 选 `main`，compare 选自己的分支，按模板填 11 条自查 | 标题带 P 编号；描述里"改了什么 / 怎么测 / 影响谁"三行都有 |
| 5 | 等 CI | PR 页面底部自动跑静态检查与提交信息校验（§5.10），**红的不许 merge** | 检查全绿 |
| 6 | 等 review | 24 小时内由 §3.5 的维护人 review；被要求改就在**同一个分支**继续 commit，PR 自动更新 | 收到 Approve |
| 7 | 合并并删除分支 | GitHub 点 **Squash and merge** → **Delete branch**；本地 `git switch main` → `git pull` → `git branch -d feat/slash-tiers` | 远程分支列表里没有它了 |
| 8 | 拉取别人的代码 | `git pull`（**每天开工第一件事也做这个**） | `git log --oneline -5` 里能看到别人的提交 |

**八步里最容易漏的三处：**

1. **第 3 步只 commit 不 push。** commit 和 push 是两件事，两个都要做。只 commit 的话 PR 页面看不到任何提交，会误判成网络问题。
2. **第 7 步只合并不删分支。** 分支会越堆越多，`git branch -a` 里一堆名字，过两天没人分得清哪个是活的。**分支存活上限 2 天（§5.1）。**
3. **第 8 步不做。** 本地 `main` 停在前几天，下次从它切分支就是在旧代码上开发，合并时冲突成倍增加。

**第 5 步 CI 查什么、误报了怎么办，见 §5.10。** 它只做静态检查（几十秒完成），**不在云端编译 Unity**——Actions 的机器没有 Unity 许可证，出包仍在本机做。

### 5.10 CI 与本地钩子（10/31 上线）

**workflow 在 `.github/workflows/ci.yml`，检查器在 `Tools/ci/`。** 触发时机：对 `main` 的 PR、`main` 上的推送，以及手动触发。只用 Python 标准库，不装任何第三方依赖。

**五项检查：**

| 检查 | 拦什么 | 边界（不会误伤） |
|---|---|---|
| 仓库卫生 | 根目录 `Library/` `Build/` `Logs/` 等入库；`.exe` `.csproj` `.psd` `.blend` 等后缀；单文件 > 50MB（>10MB 只提示） | `Build/app.exe` 会红，但 `Assets/_Project/Scripts/Build/CardPool.cs` **不会**——规则锚定仓库根 |
| `.meta` 配对 | 资源缺同名 `.meta`；删了资源却留着 `.meta` | `.gitkeep`、`.md` 不要求 `.meta` |
| 命名规范 | 路径含中文/空格/括号；文件名以 `new`/`final` 结尾；脚本不是 PascalCase；美术缺 `spr_/ui_/vfx_/tex_` 前缀；音频缺 `sfx_/bgm_` 前缀 | `sfx_renew.wav` 不会被误判成 `new`（要求前面是下划线） |
| C# 硬约束 | `public` 字段、`FindObjectOfType` 等废弃 API、`Rigidbody2D`、URP/新 Input System/DOTween/Cinemachine、`Time.timeScale` 出现在 `GameFlow.cs` 以外、命名空间不是 `FlickCut`、file-scoped namespace | `public event`、`public const`、`static readonly`、表达式属性、注释掉的代码**都不红** |
| 提交信息与文档 | PR 内每条提交信息格式（规则同 §5.2）；md 里的相对链接是否失效 | `Merge` / `Revert` 提交跳过 |

**明确不做：** 不跑 Unity 构建、不跑玩法自动化测试、不做代码风格强制（缩进、空格靠 review）。**编译错误和手感问题，仍然只有本地 Play 和 review 能发现**，别以为 CI 绿了就能合并。

**本地用法：**

```bash
bash Tools/ci/install-hooks.sh     # 装 commit-msg 钩子，每人 clone 后一次，不需要 Python
python Tools/ci/checks.py all      # 可选：本地跑全量检查（需 Python 3.9+，没装就交给 CI）
python Tools/ci/test_checks.py     # 可选：检查器自测
```

**检查器自带 16 项自测，CI 每次先跑自测、再查仓库。** 自测同时覆盖"该报的必须报"和"不该报的不能报"两类。**认为 CI 误报时，不要绕过，把那条输出贴给策划：改检查器，并补一条对应的自测。** 这样同一个误报不会出现第二次。

**最后一步必须在网页上做（一次性，仓库管理员）：**

1. 先让 CI 至少跑过一次（任意 PR 或一次 main 推送），否则第 3 步搜不到名字
2. **Settings → Branches → Add rule**（或 Rulesets → New branch ruleset），目标分支 `main`
3. 勾 **Require a pull request before merging**
4. 勾 **Require status checks to pass**，搜索并选中 **`静态检查与提交信息校验`**（与 yml 里的 job 名一致）
5. 保存

> **只放 workflow 文件、不设 required，PR 不会被拦住，等于没有门。**
