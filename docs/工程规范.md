# 《闪切协议》工程规范

> 适用于 6 人 9 天实训（Unity 6000.3.7f1 / Built-In 2D / Mono 构建）。
> 这份文件的目的只有一个：**让六个人写出来的东西长得一样，D5 合并时不打架。**
> 落地方式：把本文放到仓库 `docs/工程规范.md`，10/31 全员过一遍，之后谁新建文件就照这个来。

---

## 0. 为什么必须先定规范

不夸张地说，**六个新生项目死得最快的方式不是写不出功能，是文件找不到、名字对不上、合并冲突**。

三个真实会发生的场景：

- 美术给了你 `玩家.png`、`玩家2.png`、`玩家最终版.png`，你不知道该用哪个，全塞进项目，最后上线的那个是错的
- 两个程序都写了 `ObjectPool.cs`，Unity 报 `duplicate class`，谁也看不懂是哪来的
- 有人 `git add .` 把 `Library/`（三个 G）提交了，之后所有人 clone 都卡住

**这三件事都不需要"技术能力"来解决，只需要一份规则。** 所以规范不是形式主义，是省时间的。

---

## 1. 四条铁律（其余都可以商量，这四条不行）

| # | 规则 | 为什么不可商量 |
|---|---|---|
| 1 | **文件名一律用英文，不用中文、不用空格** | Unity 对中文路径有各种诡异问题；打包时某些工具会挂；Git 在 Windows 上对中文文件名处理不一致 |
| 2 | **文件名不允许出现版本词**：`new` `final` `old` `2` `(1)` `改` | 出现"最终版"的那一刻，就说明没有版本控制了——而你们有 Git |
| 3 | **文件名 = 类名（脚本）** | Unity 里 MonoBehaviour 挂载要求类名与文件名一致，不一致的脚本挂不上 |
| 4 | **一旦定名，不再改** | 改文件名会让 Unity 生成新的 `.meta`，引用全部断裂（预制体上的脚本会变成 `Missing`）。改名成本远高于当初想清楚 |

> 第 4 条尤其重要。**宁可名字起得笨一点，也不要第二天觉得"不太对"就重命名。** 真要改，必须走"改名 + 提交 + 全员 pull"的流程，而且没人有本地未提交改动时才能做。

## 2. 命名规范（按类型分）

### 2.1 代码

| 对象 | 规则 | 例 |
|---|---|---|
| 脚本文件 | `PascalCase`，与类名完全一致 | `PlayerController.cs`、`SlashSystem.cs` |
| 类 / 结构体 / 枚举 | `PascalCase` | `class EnemyManager` |
| 公开方法 / 属性 | `PascalCase` | `TakeDamage()`、`IsCharging` |
| 私有字段 | `camelCase` | `chargeSpeed`、`lastSlashAt` |
| 局部变量 / 参数 | `camelCase` | `worldDt`、`targetEnemy` |
| 常量 | `PascalCase` | `MaxEnemyCount`、`ChargeTier2Threshold` |
| 接口 | `I` + `PascalCase` | `IDamageable` |
| 事件 | `On` + 动词过去式 / 名词 | `OnEnemyDied`、`OnLevelUp` |

**硬要求两条：**

- **不要写 `public` 字段。** 用 `[SerializeField] private float chargeSpeed;`。public 字段会污染 Inspector，而且谁都能改，出了问题查不到。
- **类名必须带模块语义。** 写 `EnemyChaser`，不要写 `Chaser`；写 `UIScoreBar`，不要写 `Bar`。三个程序各写各的，短名字一定会撞。

**关于命名空间**：统一使用 `namespace FlickCut`，所有脚本都加，包括空文件。

> 与仓库名对齐：仓库是 `FLICKCUT-PROTOCOL`，所以代码里一律 `FlickCut`（一个单词、驼峰），**不要写 `FlashCut`、`FlickCut.Protocol`、`FLICKCUT`**。
> 顺手加一条硬的：**Unity 里 `Product Name` 填 `FLICKCUT PROTOCOL`，`Company Name` 填 `FlickCut`**，六个人建项目时都要一致——不一致会导致 `PlayerPrefs` 路径不同，D6 之后存档/设置会莫名消失。

```csharp
namespace FlickCut
{
    public class PlayerController : MonoBehaviour
    {
        // ...
    }
}
```

**要么全都加、要么全都不加，10/31 定死后不许变。** 一半加一半不加，引用会到处报"找不到类型"，而且报错信息看不出原因。

### 2.2 场景 / 预制体 / 数据资产

| 对象 | 规则 | 例 |
|---|---|---|
| 场景 | `PascalCase` | `Boot.unity`、`Arena.unity`、`Dev_A.unity` |
| 预制体 | `PascalCase`，多词用 `_` 分隔模块与具体 | `Player.prefab`、`Enemy_Chaser.prefab`、`VFX_Slash.prefab` |
| ScriptableObject 资产 | `snake_case`，带类型前缀 | `upgrade_widen.asset`、`config_base.asset` |
| 材质 | `mat_` + `snake_case` | `mat_enemy_cyan.mat` |
| 动画剪辑 | `anim_` + `snake_case` | `anim_player_idle.anim` |

**`Dev_*` 场景的规则**：每人一个（`Dev_A` / `Dev_B` / `Dev_C`），自己随便玩，**可以提交，但不能出现在最终构建里**。

### 2.3 美术资源（两个人以上协作时最容易乱）

统一用 **`前缀_小写下划线`**。前缀决定它是哪类东西：

| 前缀 | 用途 | 例 |
|---|---|---|
| `spr_` | Sprite 单图（角色、敌人、场景件） | `spr_player_base.png`、`spr_enemy_chaser.png` |
| `ui_` | UI 元素（面板、按钮、卡面、HUD） | `ui_card_bg.png`、`ui_hp_bar_fill.png` |
| `vfx_` | 特效贴图 | `vfx_slash_glow.png` |
| `tex_` | 平铺底图 / 网格 | `tex_arena_grid.png` |

**同一角色的多帧/多变体，用后缀区分，不要用数字堆：**

```
spr_player_base.png
spr_player_charge.png      ← 蓄力状态的形态
spr_enemy_chaser_base.png
spr_enemy_chaser_hurt.png
```

**不许出现的中文名**（真实会发生的）：

```
❌ 玩家.png        ✅ spr_player_base.png
❌ 三角形敌人.png   ✅ spr_enemy_chaser.png
❌ 刀光-宽.png      ✅ vfx_slash_wide.png
❌ 新文件夹 (2)      ✅ （不要建这个文件夹）
```

### 2.4 音频

| 前缀 | 用途 | 例 |
|---|---|---|
| `sfx_` | 短音效（≤ 3 秒） | `sfx_slash_tier1.wav`、`sfx_hit_soft.wav` |
| `bgm_` | 背景音乐（循环） | `bgm_arena_loop.ogg` |

**三段蓄力的音效要能对上**：`sfx_charge_tier1` / `tier2` / `tier3`。这样程序接入时不用问美术"哪个是第一段"。

## 3. 存放规范

### 3.1 判定一个文件该放哪（照着走，不要自己建目录）

```
这个文件是……
├─ C# 脚本        → Assets/_Project/Scripts/<模块>/
├─ 图片            → Assets/_Project/Art/<分类>/
├─ 音频            → Assets/_Project/Audio/SFX/ 或 Music/
├─ 预制体          → Assets/_Project/Prefabs/
├─ 材质 / 动画      → Assets/_Project/Art/ 对应子目录
├─ 数值配置        → Assets/_Project/Data/
├─ 文档            → docs/
├─ 只是自己试验的    → Assets/_Scratch/<你的名字>/
└─ 不确定           → 问技术负责人，不要自己建目录
```

**最后一条是纪律，不是客气。** 六个人各建一个"我觉得这样更合理"的目录，D4 就没人找得到东西了。

### 3.2 模块目录只有六个，不许新增

`Scripts/` 下只允许这六个：

```
Scripts/
├─ Core/      GameFlow.cs  ObjectPool.cs  GameConfig.cs
├─ Player/    PlayerController.cs  ChargeController.cs
├─ Combat/    SlashSystem.cs  IDamageable.cs  HitFeedback.cs
├─ Enemy/     EnemyBase.cs  EnemyChaser.cs  EnemyTank.cs  EnemyManager.cs
├─ Build/     UpgradeDef.cs  UpgradeManager.cs
└─ UI/        HUD.cs  LevelUpPanel.cs  ResultPanel.cs
```

一个脚本放哪个模块，看**它属于谁的生命周期**，不是看谁写的：

- 敌人身上的逻辑 → `Enemy/`（哪怕是我写的）
- 屏幕上显示的 → `UI/`
- 两个模块都要用的工具 → `Core/`

### 3.3 临时区 `_Scratch`（必须有，而且要进 .gitignore）

新生一定会写测试脚本、放临时贴图。**不给地方，他们就会丢进正式目录。**

```
Assets/_Scratch/<你的名字>/      ← 例如 Assets/_Scratch/mqz/
```

`.gitignore` 加一行：

```
Assets/_Scratch/
```

好处有两个：谁都敢在里面乱试；而且**不会有人把测试脚本提交上去，让技术负责人猜"这个 TestSlash2.cs 要不要删"**。

### 3.4 仓库里不该有的东西（`git add .` 前必看）

| 不该有 | 后果 |
|---|---|
| `Library/` `Temp/` `Obj/` `Logs/` `UserSettings/` | 几百 MB 到几个 G，每人不同，提交必冲突 |
| `*.csproj` `*.sln` `*.user` `.vs/` | Unity 自动生成，提交必冲突 |
| `Build/` 里的 exe | 走 Release 附件 |
| 大于 50MB 的 PSD / AI 源文件 | 走网盘，仓库只放导出后的 png |
| `Assets/_Scratch/` | 临时区不进仓库 |
| 授权不明的字体、音乐 | 答辩会被问来源 |

### 3.5 功能分级与代码归属（P0 / P1 / P2 ↔ 文件）

**排期按 P 编号走（见启动方案 §1.5）。这一节解决"某个 P 编号该改哪个文件"，避免两个人改同一个文件。**

| 编号 | 功能 | 主要落在哪个文件 | 谁维护 |
|---|---|---|---|
| **P0-1** | 移动 + 瞄准 | `Player/PlayerController.cs` | 程序 1 |
| **P0-2** | 蓄力 → 释放 | `Player/ChargeController.cs` | 程序 1 |
| **P0-3** | 切割命中 | `Combat/SlashSystem.cs`、`Combat/IDamageable.cs` | 程序 1 |
| **P0-4** | 死亡 → 经验 | `Enemy/EnemyBase.cs`、`Enemy/EnemyManager.cs`、`Build/UpgradeManager.cs`（经验条） | 程序 2 |
| **P0-5** | 升级三选一 | `Build/UpgradeDef.cs`、`Build/UpgradeManager.cs`、`UI/LevelUpPanel.cs` | 程序 2 |
| **P0-6** | 一局闭环 | `Core/GameFlow.cs`、`UI/ResultPanel.cs` | 程序 2（`GameFlow` 改动须程序 1 过目） |
| **P0-7** | 三色可分辨 | `Art/` 与 `Data/GameConfig.asset` 里的颜色 | 美术 A |
| **P0-8** | 能出包 | Build Profiles、`README.md` 的"怎么跑" | 程序 3 |
| **P0-9** | 能重开 | `Core/GameFlow.cs` 的 `ResetRun()`、`Core/ObjectPool.cs` | 程序 3 测 / 程序 1 修 |
| **P1-1** | 三段蓄力 | `Player/ChargeController.cs` | 程序 1 |
| **P1-2** | 4 张卡 | `Build/UpgradeDef.cs` + `Data/Upgrades/*.asset` | 程序 2 |
| **P1-3** | 两类敌人 | `Enemy/EnemyTank.cs`、`Enemy/EnemyManager.cs` | 程序 2 |
| **P1-4** | 打击四件套 | `Combat/HitFeedback.cs` | 程序 1 |
| **P1-5** | 连穿增伤 | `Combat/SlashSystem.cs` | 程序 1 |
| **P1-6** | HUD 完整 | `UI/HUD.cs` | 程序 3（代码由程序 1 给，他只绑引用） |
| **P1-7** | 暂停 + 音量 | `Core/GameFlow.cs` 的 `Paused` | 程序 3（同上） |

**三条由此推出的规矩：**

1. **同一时刻，一个文件只有一个主人。** 想改别人的文件，先在群里说，对方当天不做那块。
2. **`GameFlow.cs` 是全场唯一的多入口文件**，所有改动都要程序 1 过目——因为时间缩放、暂停、结算、重开全挤在这一个文件里，冲突也全在这里。
3. **P1-6 / P1-7 的代码不由程序 3 写。** 程序 1 给一个 `HUD.SetXXX()` 接口，程序 3 在 Inspector 里把 Text 拖上去。**这不是看不起他，是保证他当天能交东西。**

## 4. C# 代码规范（精简到能记住的程度）

不强求风格统一到"每行几个空格"，只要求下面这几条，因为它们直接影响**能不能改得动**。

### 4.1 文件结构

```csharp
using UnityEngine;

namespace FlickCut
{
    /// <summary>玩家移动、瞄准与蓄力输入的入口。</summary>
    public class PlayerController : MonoBehaviour
    {
        [SerializeField] private float moveSpeed = 220f;
        [SerializeField] private float chargeSlowFactor = 0.65f;

        private bool isCharging;
        private float chargeProgress;

        public bool IsCharging => isCharging;
        public float ChargeProgress => chargeProgress;

        private void Update()
        {
            // ...
        }

        public void BeginCharge() { /* ... */ }
    }
}
```

### 4.2 五条硬要求

1. **一个文件一个 `public` 类**，文件名与类名相同。
2. **不写 `public` 字段**，用 `[SerializeField] private` 暴露给 Inspector。
3. **不用 `Region`**。需要分区的类，说明它该拆了。
4. **每个 `public` 方法上方写一行中文 `/// <summary>`**。不是为了好看——**是为了 D8 出 bug 时，别人（或明天的你）能看懂这是在干什么**。
5. **魔法数字要么进 `GameConfig`，要么写成常量**。`if (progress >= 0.65f)` 里的 `0.65` 必须能查到出处（数值表里有）。

> 第 5 条是这次特别要盯的。手感参数会反复调，散落在十个文件里的 `0.65` 根本改不动。

### 4.3 明确不做的事

- 不写单例管理器（除了 `GameFlow` 一个，且由技术负责人维护）
- 不写通用框架、事件总线、数据驱动卡池（**4 张卡写死就行**）
- 不用 `FindObjectOfType` 到处找对象（Unity 6 里这个方法已废弃，改用引用或事件）

## 5. Git 规范

### 5.0 装完 Git 的第一次配置（每人做一次，三行）

装完 Git for Windows 后，打开 Git Bash 执行（把名字和邮箱换成自己的）：

```bash
git config --global user.name  "马权"
git config --global user.email "你的GitHub邮箱"
git config --global core.autocrlf false
git config --global core.longpaths true
```

| 这行为什么必须有 |
|---|
| **`user.name` / `user.email`** 不配的话，六个人的提交全显示成别人的名字，`git log` 查不到责任人。**邮箱用注册 GitHub 的那个**，否则 GitHub 不认这个提交是你的 |
| **`core.autocrlf false`** 仓库里已经有 `.gitattributes` 统一成 `eol=lf`，这里再让 Git 自动转换会两边打架，表现是"我没改的文件显示全变了" |
| **`core.longpaths true`** Unity 的 `Library/` 和素材路径很深，超过 260 字符时 Windows 会报"文件名过长"，git 直接卡住 |

**克隆用 HTTPS，不要用 SSH：**

```bash
git clone https://github.com/jmx2033/FLICKCUT-PROTOCOL.git
```

SSH 要生成密钥、贴到 GitHub、改 `config`，新生至少卡一小时。HTTPS 第一次 `push` 会弹出浏览器让你登录一次，之后 Credential Manager 会记住。**注意：GitHub 早就不支持在命令行输账号密码了**，弹窗里要选 "Sign in with your browser"，不是输密码。

### 5.1 分支

| 类型 | 格式 | 例 | 谁用 |
|---|---|---|---|
| 功能 | `feat/<模块>-<简述>` | `feat/slash-tiers` | 程序 |
| 修复 | `fix/<简述>` | `fix/exp-orb-pool` | 程序 |
| 美术 | `art/<内容>` | `art/player-sprite` | 美术 |
| 文档 | `docs/<内容>` | `docs/scope-list` | 策划 |

**三条纪律：**

- **每人同时只允许 1 个活跃分支**，合并完再开下一个
- **分支存活不超过 2 天**，超过就说明拆分有问题
- **分支只从最新的 `main` 开**，不从别人的分支开

### 5.2 提交信息

格式固定：

```
<type>(<scope>): <一句话说清改了什么>
```

| 字段 | 可选值 |
|---|---|
| `type` | `feat` 新功能 / `fix` 修 bug / `art` 美术资源 / `docs` 文档 / `chore` 杂务 / `refactor` 重写不改行为 |
| `scope` | `charge` `slash` `enemy` `ui` `build` `repo` `levelup` |

**正例：**

```
feat(slash): 三段刃形按蓄力进度切换
fix(enemy): 敌人死亡后经验球未回收
art(player): 玩家基础造型 64px
docs(scope): 补做/不做清单
chore(repo): 忽略 Library 与 _Scratch
```

**反例（真的会有人这么写）：**

```
❌ update
❌ 改了一下
❌ 111
❌ 最终版
❌ 修复了一些问题
❌ asdf
```

判断标准很简单：**三天后你自己能不能看懂这条提交在干什么。**

### 5.3 提交前必做（`git add` 之前）

```bash
git status          # 先看一遍，确认没有 Library、没有 exe、没有 .csproj
git add <具体文件>   # 尽量不用 git add .
git commit -m "feat(slash): 三段刃形按蓄力进度切换"
```

**关于 `git add .`**：不是禁用，但**每次用它之前必须先 `git status` 看一眼**。六个人里一定有人会在某天用它把 `Library/` 提交上去，那天所有人的 clone 都会变慢十倍。

### 5.4 PR（Pull Request）

- 标题同提交规范，**末尾标 P 编号**：`feat(slash): 三段刃形按蓄力进度切换 [P1-1]`
- 描述三行：
  ```
  改了什么：蓄力进度映射到三段刃形
  怎么验证：Arena 场景按住左键，看刀的长宽变化
  截图/录屏：有视觉变化时必传
  ```
- **至少 1 人 review 后才能合并**（三个程序互审，美术/文档可由策划审）
- **24 小时内必须有人看**。超时没人看的 PR，说明分工出了问题
- **一个 PR 只做一件事**，超过 400 行就拆

### 5.5 六条禁止（写进 PR 模板底部）

```
[ ] 没有提交 Library/ Temp/ Obj/ *.csproj *.sln
[ ] 没有提交 Assets/_Scratch/
[ ] 没有修改 Arena.unity（除非我是技术负责人）
[ ] 没有 force push
[ ] 没有残留冲突标记 <<<<<<< 或 >>>>>>>
[ ] 本地能跑起来（拉最新 main 后编译通过）
```

### 5.6 每天的时间节奏

| 时间 | 做什么 |
|---|---|
| 早上开工 | `git pull` → 打开项目确认能跑 → 有错先修，不要开始写新东西 |
| 写的过程中 | 每完成一个小功能就 commit + push（**不攒到晚上**） |

**"攒到晚上一次推"是新手最常见的坏习惯。** 攒了一天的改动，冲突时几乎无法解决；每两小时推一次，冲突只有几行。

### 5.7 场景文件与预制体的特殊规则

`.unity` 和 `.prefab` 是**二进制式文本，无法有效合并**。所以：

| 文件 | 谁可以改 |
|---|---|
| `Arena.unity` | **只有技术负责人** |
| `Dev_A/B/C.unity` | 各自的主人 |
| `Player.prefab` | 技术负责人 |
| `Enemy_*.prefab` | 系统程序 |
| UI 预制体 | 工具/测试程序 + 美术B |
| 别人的预制体 | **改之前先在群里说一声** |

> 这条不遵守的后果很具体：两个人同时改 `Arena.unity`，合并时 Git 会说 `Cannot merge binary files`，最后只能丢掉一个人的全部改动。

### 5.8 美术提交的特殊提示

美术同学最容易踩的两件事：

1. **提交前先改名成规范格式**，不要提交 `新建图层1.png` 再让程序改
