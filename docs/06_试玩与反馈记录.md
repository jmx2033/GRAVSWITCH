### F-01 · 手感「有点卡」

- **原话**（18:12 前后）：
  - 「我玩了一下那个 demo」
  - 「感觉还行但手感上面似乎有点卡」
  - 「不知道什么引起的」
- **我方追问**：「是不是同时命中多个敌人的时候会卡？」→ **对方未回答**，原因未定位。
- **已知事实**：V0.3 版本已修过一次连切卡顿（原因是色差效果触发全画布二次重绘 + 全画布滤镜，改为战场单绘、色差只作用于切割残光；HUD 改为每帧最多刷新一次）。修复后压测：20 目标 × 5 连切、2× DPR 下 p95 帧间隔 16.7ms。
- **假设（未证实）**：
  1. **真实掉帧**：低配机器 / 高 DPR 屏 / 同时命中大量目标时的叠加特效 —— **因报告者是主程，此项权重上调**。
  2. 对方测试的是**修复前**的版本，卡顿已不存在 —— 需确认测试时间点与文件来源。
  3. 「卡」不等于掉帧，可能是**输入延迟感 / 蓄力减速带来的粘滞感**（蓄力时世界时间 ×0.2、玩家操控系数 0.65）—— 权重下调，但不能排除。
- **注意**：主程说「不知道什么引起的」，说明他**没有做过测量**，只停留在体感层面。这条的价值是"信号存在"，不是"病因已明"。真正的定位仍然要靠帧时间数据，而不是靠讨论。
- **交叉证据（2026-10-27，来自 P-01）**：试玩者 B 玩完一整轮，评价是「原型很不错」「切人是有挺高正反馈的」，**完全没有提到卡顿**。两个样本给出相反信号。这让 F-01 的解释重心往回摆：
  - "普遍掉帧"的可能性下调——若是普遍现象，第二个样本大概率也会撞上；
  - "设备 / 版本差异"与"蓄力减速被描述成卡"的可能性上调；
  - 但**不能据此结案**：B 是新玩家，对帧率不敏感，也可能根本没打到高密度敌人。
  - 结论：F-01 从 P1 降为**观察项**，等主程给版本时间点或一次帧时间录制再定级。
- **待确认**（下次直接问这三句）：
  - 用的是哪个文件、大概几点玩的？
  - 是**画面一顿一顿**，还是**操作跟手变慢**？
  - 卡的时候屏幕上大概多少敌人？是不是刚放完一刀？
- **处置建议**：不改代码，先拿到上面三个答案。若确认是掉帧，再按「命中数量 / DPR / 特效开关」三档做定位，不要盲改。若主程愿意配合，直接让他开 DevTools 的 Performance 录一段连切——比三个问题加起来都快。

### F-02 · 重开后经验球残留（P0）

- **原话**：
  - 「虽说我不是很懂有些可能是瞎讲」
  - 「这个经验球重开游戏还会在地图上」
  - 「这些算小问题吧」
- **为什么仍定 P0**：对方自己判断为"小问题"，但如果成立，属于**重开状态污染**——多次试玩后地图上残留旧局经验球，会直接影响经验节奏与对"升级手感"的判断，而升级手感正是阶段 0 的核心验收项。所以不能按"小问题"处理。
- **身份带来的权重变化（重要）**：报告者是**团队主程**。他说的「虽说我不是很懂有些可能是瞎讲」更接近退让式表达，而非能力不足——他不会把没有发生的现象说成 BUG。因此**「重开后确有东西没清」这一层基本可以采信**，剩下的争议只在"清到什么程度"。
- **已知事实（有冲突，必须对齐）**：本地 V0.3 自动化回归中做过**连续 10 次重开**，断言为对象池、经验球、音源全部清空，当时通过。
- **冲突怎么解释（当前最可能的解释，未验证）**：自动化只覆盖了**跑满 3 分钟后的重开**，很可能漏了**中途死亡后重开**这条分支——即 `reset()` 在失败路径上的清理不完整。这能同时解释"他看到了"和"我们测不到"。
- **假设（未证实）**：
  1. **失败结算后重开**分支的经验球未被清理（优先级最高）。
  2. 对方走的是**刷新页面 / 关掉重开**，而非游戏内重开按钮。
  3. 视觉残留（球停在原地未被清理）vs 逻辑残留（重开后仍能吃到、仍计入经验）——**这两种严重程度差很远**，必须分清。
- **待确认**：
  - 是"跑完 3 分钟重开"还是"中途死亡重开"还是"刷新页面"？
  - 残留的球**还能不能吃**？吃了会不会加经验？
  - 残留是几颗、在哪个位置？
- **处置建议**：主程既有报告也有代码环境，**不要让他等我们复现**——直接请他按上面三问各走一遍，同时看 `reset()` 在失败分支里有没有重置经验球数组。我们这边同步补一条"中途死亡后重开"的自动化断言，堵住这个覆盖漏洞。

### F-03 · 冷却期间也要有瞄准

- **原话**：「我觉得技能冷却的时候也可以加个瞄准」
- **理解（待对方确认）**：目前冷却 / 不可切状态下，准星或瞄准指示消失，玩家失去"我下一秒要往哪切"的空间感；建议**冷却期仍保留瞄准指示**，只是不可释放。
- **判断**：方向合理，且与阶段 0 的核心问题（愿不愿意蓄力）正相关——瞄准持续可见 = 玩家在冷却期就在规划下一次切入，能减少"等冷却"的空转感。
- **风险**：瞄准常驻可能削弱"蓄力时世界减速、需要提前定线"的紧张感；也可能与蓄力预告线视觉打架。
- **状态**：归档，**不进阶段 0**（阶段 0 的硬门槛是验证蓄力意愿与闪切爽感，加瞄准辅助会污染判断）。建议放到阶段 1 与"完美窗口 UI"一起讨论。

## 五、F-05 · 升级弹窗打断操作并导致误触（P0，已定位根因）

- **原话**：「然后如果对原型苛刻一点的话，我觉得**交互现在很史**，经常**突然跳出来升级**，而我**正在切刀**，然后**误触升级**。」
- **我方回应**：「这确实是」

### 代码级根因（已核对 `demo.html` 实际实现）

四处叠加，按危害排序：

1. **蓄力被无偿取消**（最伤）。
   主循环里 `if(G.pendingLevels>0 && mode==='playing') openUpgrade();` → `openUpgrade()` 第一行就是 `cancelCharge()`。
   玩家蓄到三段、正准备放出去的那一下，被系统直接作废——**时间和风险都白付了**。玩家描述成"正在切刀被弹窗打断"，实际体验是"我的手被拿走了"。
2. **弹窗完全不看时机**。
   经验满的**同一帧**就弹，不管玩家是否在蓄力、是否正穿过敌群、鼠标左键是否按着。这个检查里只有 `mode==='playing'`，没有任何"玩家状态"条件。
3. **卡片是点击即选，没有保护期**。
   卡片用 `onclick` 绑定（`b.onclick=()=>chooseUpgrade(i)`）。玩家松手那一下的惯性点击、或紧接着的习惯性单击，都会直接选中一张卡，且**不可撤销**。
4. **连续升级时立刻再开一窗**。
   `chooseUpgrade()` 里 `if(G.pendingLevels>0){mode='playing';openUpgrade();}` → 连升两级时，第二个窗瞬间再开，玩家连点会**连选两张**，连"看看再选"的余地都没有。

### 为什么这条是 P0，排在 F-02 前面

**它污染的是阶段 0 正在测量的东西。** 阶段 0 第一条门槛是"愿不愿意蓄力"。如果蓄力会被系统随机作废，玩家的理性策略就是**少蓄力、短蓄力**——他们的"蓄力意愿"会被系统性地压低，而我们测到的数字是假的。

**用坏掉的能力测量工具去测，比没有数据更危险**，因为它会得出一个看起来有数据支撑的错误结论（"玩家不愿意蓄力"），进而误判整个核心机制的可行性。

### 修复方案（按最小改动设计，不动核心判定）

1. **加安全窗口再弹**：`pendingLevels>0` 时先不弹，等到 `!p.charging && 距上次切割 > 0.35s && 距上次命中 > 0.2s` 再弹；同时加兜底——待弹超过 1.5 秒强制弹出，避免玩家一直按住鼠标导致永不升级。
2. **卡片保护期 300ms**：`openUpgrade()` 记录开窗时间，`chooseUpgrade()` 在 300ms 内忽略输入。专门挡住"松手惯性点击"。
3. **连续升级加间隔**：`pendingLevels>0` 时不立刻重开，延迟 250ms，让玩家看清"又升了一级"。
4. **保留 `cancelCharge()` 作为兜底**：第 1 条生效后它实际不会触发，但留着防万一。

预估改动约 20 行，全部在"何时弹窗 / 何时接受点击"这一层，**不碰伤害、判定、敌人生成**，回归风险低。

### 版本一致性（已确定）

`demo.html` 已升到 **V0.3.1**：

- **前 2 个样本（A、B）跑的是 V0.3**，蓄力意愿数据受 F-05 污染，**不参与"愿不愿意蓄力"的统计**，只作为"闪切正反馈成立"的证据保留；
- **第 3–5 个样本跑 V0.3.1**（含 F-05 修复），这才是门槛判定的有效样本。

### 修复实现（V0.3.1，已落地）

改动集中在"何时弹窗 / 何时接受点击"一层，**未触碰伤害、判定、敌人生成、经验曲线**：

| 项 | 实现 |

| 蓄力保护 | `openUpgrade()` 仅在真的打断蓄力时才 `cancelCharge(true)`，并补取消音；正常路径下蓄力早已结束，不会触发 |
| 卡片保护期 | `openUpgrade()` 记 `G.upgradeAt`，`chooseUpgrade()` 在 300ms 内忽略输入（挡住松手惯性点击） |
| 连续升级 | 不再立刻重开窗，改为 `upgradeLockUntil = now+250ms`，回到战斗 250ms 后才允许再弹 |
| 新状态字段 | `pendingSince` / `upgradeAt` / `upgradeLockUntil` / `lastSlashAt` / `lastHitAt`，均在 `newGame()` 中归零 |

### 回归验证结果（Chrome headless + CDP，全部通过）
