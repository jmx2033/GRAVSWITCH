# 13 · 重力区视觉实现参考

> 记录 `Scripts/level/gravity_zone_visuals.gd` 里**每个数值为什么这么定**，以及踩过哪些坑。
> 代码里只留一行注释，长解释都搬到这里——改数值前先看这份。
>
> 拆分成两个文件的原因、职责边界也在这里说明。
>
> **11/6 现状**：晶核（中央白色光斑）已按负责人要求**整体移除**。

## 一、文件分工

| 文件 | 职责 | 不做什么 |
|---|---|---|
| `Scripts/level/gravity_zone.gd` | 碰撞形状、玩家进出判定、石粒数据生成与位置推进、`_pull()` 方向换算 | 不画任何东西 |
| `Scripts/level/gravity_zone_visuals.gd` | 只负责 `_draw()`：场体渐变、出口辉光、石粒拖尾、边框四角、编辑器箭头 | 不参与碰撞与重力逻辑 |

数据单向流动：`gravity_zone.gd` 持有 `_stones` 数组并每帧推进位置，通过 `set_stones()` 把**同一个数组**交给视觉层；视觉层只读不写。

### 为什么不写 `class_name`

`gravity_zone_visuals.gd` **刻意不写 `class_name`**。两个脚本互相引用时，`class_name` 的解析顺序不确定，会报：

```
SCRIPT ERROR: Parse Error: Could not find type "GravityZoneVisuals" in the current scope.
```

解决办法是两边都用 `preload` 脚本常量 + 类型标注写 `Node2D`，不依赖全局类型名。

## 二、场体渐变

| 常量 | 值 | 为什么 |
|---|---|---|
| `FIELD_ALPHA` | `0.45` | 曾试 0.62，把握在亮端的紫色冲淡成灰白（"画面太白了，没有紫色了"）。0.45 既看得清场体又保住紫调 |
| `FIELD_FAR_COLOR` | `#0D0A1A` | 远端要够暗，方向才能"扫一眼读出" |
| `FIELD_NEAR_COLOR` | `#B295F0` | 力源端用**鲜明的紫**而不是白；白色会毁掉磁场主色调 |
| `GRADIENT_CURVE` | `1.0` | **必须是线性**，见下 |
| `GRADIENT_SEG_TARGET_PX` | `2.0` | 每段约 2px；段太宽会看出色块状条带 |
| `GRADIENT_SEG_MAX` | `200` | 超长场的顶点数上限 |

### 两个踩过的坑

**坑 1：不能只调 alpha 做明度。**

alpha 只改变"与背景的混合比例"，颜色固定为暗紫时 alpha 拉满也还是暗的——做不出"亮→暗"。必须**插值颜色本身**（`far.lerp(near, t)`）。

**坑 2：曲线必须是 1.0，而且不能用逐像素 `draw_rect`。**

- 试过 `GRADIENT_CURVE = 0.34`（想让亮度往力源端集中）：幂曲线在远端斜率无穷大，用有限段做线性近似会出现**明显折线台阶**。
- 试过 24 段逐段 `draw_rect`：每段是"平涂一色"，段太宽（约 13px）就看出色块状竖条纹，负责人反馈"水平方向竖条纹间距明显"。
- 现在：`draw_polygon` 顶点色让 GPU 插值 + 段数按每段 2px 自适应。实测 RIGHT 区沿轴亮度 `24→25→26→…→88`，相邻跳跃 >2.5 的处数为 **0/74**。

### 长场方向可读性（重要）

早期用 `GRADIENT_CURVE = 0.34` 时，短场好看，**场一长就看不出方向**——亮度全挤在力源端，中段是均匀灰紫。

线性渐变保证任何长度都单调等速变亮。实测三种长度：

| 场长 | 亮度序列 | 单调 | 两端差 |
|---|---|---|---|
| 4 格 | 22→33→44→55→66→77→88 | ✅ | 66 |
| 9 格 | 同上 | ✅ | 66 |
| 10 格 | 21→…→88 | ✅ | 67 |

## 三、出口辉光

| 常量 | 值 | 为什么 |
|---|---|---|
| `GLOW_COLOR` | `#D9CBFF` | 比场体亮一档，但不发白 |
| `GLOW_ALPHA` | `0.42` | 低于 0.4 会被场体渐变盖住、几乎看不见 |
| `GLOW_WIDTH` | `64.0` | 往场内延伸的厚度；负责人手动调过 |
| `GLOW_PULSE_SPEED` / `AMOUNT` | `0.7` / `0.35` | 呼吸：整体明暗起伏 |
| `GLOW_FLOW_SPEED` / `WAVES` / `DEPTH` | `0.9` / `1.5` / `0.55` | 游走：沿边界切段，按相位平移的亮纹 |
| `GLOW_SEG_PX` | `8.0` | 切段长度；越小光纹越细腻 |

### 踩过的坑：不要用多层 `draw_rect` 叠辉光

早期用 10 层 `draw_rect` 逐层平涂叠出辉光，**相邻层的 alpha 差形成一条条可见条纹**，负责人反馈"辉光太怪，去掉吧"。

现在改成 `draw_polygon` **顶点色**：贴边两个顶点不透明、场内两个顶点全透明，由 GPU 线性插值，得到连续柔光、没有任何台阶。

动效是两层叠加，不是原地明灭：

- **呼吸**：`sin(_time * GLOW_PULSE_SPEED)` 调整体 alpha
- **游走**：沿边界切段，每段按 `sin(s * TAU * WAVES + phase)` 明暗，`phase` 随时间推进 → 亮纹**平移**，看起来在流动

## 四、石粒与拖尾

| 常量 | 值 | 为什么 |
|---|---|---|
| `STONE_SPEED` | `10.0` | 沿重力方向的漂移速度 |
| `STONES_PER_TILE` / `MAX_STONES` | `3` / `24` | 每格 3 颗，但总数封顶 24（6×9 的场按 3 颗/格会到 162 颗，那是沙尘暴） |
| `STONE_SIZE_MIN` / `MAX` | `2.0` / `4.0` | 每颗独立随机。上限曾试 8px，在 640×360 下像撒了一地马赛克；4px 才是尘埃的尺度 |
| `STONE_COLOR` / `ALPHA` | `#fff2e0` / `0.55` | 暖白，能在紫场体上被一眼看到 |
| `TRAIL_SEGMENTS` / `LENGTH` | `4` / `14.0` | 拖尾朝**重力反方向**，模拟"被甩在后面" |
| `TRAIL_ALPHA` | `0.42` | 首段透明度，之后按比例递减 |
| `TRAIL_THICK_RATIO` | `0.62` | 拖尾比石粒细，否则像拖着一根木棍 |

拖尾粗细按**每颗石粒自己的尺寸**缩放（`size * TRAIL_THICK_RATIO * (1 - t*0.55)`，最小 1px），所以大小不一的石粒不会出现尾巴比身子还粗的情况。

边界回绕也按各自的尺寸算（`limit = zone_size - Vector2(size, size)`），避免大颗粒在边界露出半颗。

## 五、边框、四角与力源端亮边

**11/6 现状：运行时不再画四角和力源端加粗边，边框也再弱化了一次。**

| 常量 | 值 | 为什么 |
|---|---|---|
| `FRAME_ALPHA` | `0.10` | 曾用 0.22，负责人仍觉得"边框有点突兀"，再降到 0.10——只作极淡的边界暗示 |
| `EDGE_HIGHLIGHT_WIDTH` | `0.0` | 力源端加粗边**已停用**（见下） |
| `CORNER_ALPHA` | `0.0` | 四角方块**已停用** |
| `CORNER_SIZE` | `4.0` | 仅编辑器预览用 |
| `EDGE_HIGHLIGHT_COLOR` | `#D9C7FF` | 同 `GLOW_COLOR` 一档 |

### 为什么去掉加粗边和四角

负责人反馈"底部的加厚太突兀"。根因是**方向感已经由场体渐变 + 出口辉光承担了**，再叠一条加粗边就是重复编码同一信息，视觉上反而刺眼。

去掉后方向依旧可读——实测四个方向的沿轴亮度都单调（RIGHT `20→108`、DOWN `17→105`、LEFT `102→15`）。

### 踩过的坑：alpha 累积成白条

力源端亮边曾分 3 层画，**每层必须从不同的 `depth` 起步**（`depth = i`）——若都从 `depth=0` 画，alpha 会叠 3 次（0.55 + 0.42 + 0.30 ≈ 1.3），直接叠成一根近乎纯白的粗条，这正是"太厚"的来源之一。

（现在运行时已不画这条边，但编辑器预览仍在用，所以这条经验保留。）

## 六、已移除：晶核（中央白色光斑）

`Scripts/level/gravity_zone_visuals.gd` 里原本有 5~9 颗"能量晶核"（多层同心圆叠出的白色柔光，带脉动与漂移）。负责人先后反馈：

1. "中心光点太闪了" → 降 `CORE_ALPHA`、加大衰减
2. "重力场中央偏出口的白色光斑太奇怪了" → 改成运动态（让它在动）
3. **"晶核还是直接去掉吧"** → 11/6 整体移除

移除范围：`CORE_*` 全部常量、`_cores` 数组、`_spawn_cores()`、`_update_cores()`、`_draw_cores()` 及其调用。

如果以后要加回类似元素，注意事项：

- 会动才不怪（静止的光斑固定在中央非常显眼）
- 一定要低 alpha + 大衰减，否则在紫场体上就是一串白灯泡
- 数量与大小反相关：多而小 = 弥散微光，少而大 = 扎眼

## 七、编辑器与运行时的差异

| 场景 | 画什么 |
|---|---|
| 编辑器 (`@tool`) | 场体渐变 + 出口辉光 + 2px 亮边框 + 四角 + 力源端亮边 + **方向箭头**；**不撒石粒**（每次重绘都重新随机会闪） |
| 运行时 | 场体渐变 + 出口辉光 + **极淡描边（alpha 0.10）** + 石粒与拖尾；**不画四角、不画力源端加粗边、无箭头** |

## 八、改数值时的自查清单

改完在 Godot 里跑一次，重点看：

1. **四个方向都试**（向上/右/下/左）——方向映射错是最容易犯的错，建议采样像素验证，不要只靠肉眼
2. **长场也要看**（10 格高）——短场好看不代表长场可读
3. **有没有可见条纹**——渐变段宽、辉光层级都是嫌疑对象
4. **主色调还在不在**——任何"提亮"操作后确认紫色没变成灰白
5. **640×360 下看**，不要只看 1280×720 的缩放结果
